# Settings architecture (3-layer merge)

`~/.claude/settings.json` symlinks to `dotfiles/.claude/settings.local.json` — generated by `modules/claude-settings/merge.sh`.

| Layer | File | Tracked? | Purpose |
|---|---|---|---|
| Base | `settings.base.json` | yes | Shared: plugin enablement, permissions, memory model, marketplaces |
| Platform | `settings.{darwin,linux,wsl}.json` | yes | OS-specific: hook paths, platform MCPs, statusLine |
| Override | `settings.override.json` | gitignored | Per-host manual tweaks |
| Generated | `settings.local.json` | gitignored | Output. NEVER hand-edit — wiped on SessionStart |

Precedence: `base → platform → override` (later wins).
Merge strategy per key in `_merge-config.json` (`concat-dedupe` / `replace-by:command` / `deep-merge-by-key` / `shallow-merge`).
Tracked fragments keep `$VAR` literal — Claude Code resolves env vars at runtime. Never pre-expand to `/Users/...`.

## Rules
1. NEVER edit `settings.local.json` directly
2. Shared rule → `settings.base.json`
3. Platform rule → `settings.{platform}.json`
4. Per-host one-off → `settings.override.json` (gitignored, never commit)
5. Keep `$VAR` literal in tracked fragments
6. After editing tracked layer: `./modules/claude-settings/doctor.sh --fix` or wait for SessionStart hook
7. Drift reported → pick correct layer, then `--fix`. Don't paper over by hand-editing `settings.local.json`
8. Cross-host: edit → commit → push → other hosts pull + regenerate on next session

When in doubt: `./modules/claude-settings/doctor.sh` first.
