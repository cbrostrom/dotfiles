# Shopify Theme Development

Comprehensive reference for developing Shopify Online Store 2.0 themes in the Stellar multi-store architecture. This skill complements the Cursor rules (`shopify-best-practices.mdc`, `multi-store-architecture.mdc`, `code-quality.mdc`) with deeper patterns and rationale.

## When to Use

- Creating or editing Liquid templates, sections, snippets, or blocks
- Authoring TypeScript schemas for sections or theme settings
- Working with Shopify APIs from theme JavaScript (cart, search, section rendering)
- Optimizing theme performance (Lighthouse, Core Web Vitals)
- Managing locale/translation files
- Configuring the Vite asset pipeline for Shopify

## Project Architecture

### Store Structure

Each store follows the fork-and-diverge model. Stores are independent after creation:

```
stores/{store}/
  src/
    schemas/           # TypeScript schema definitions
      sections/        # Section schemas (→ {% schema %} in .liquid)
      settings/        # Reusable setting factories
      configs/         # Theme config schemas (→ settings_schema.json)
      blocks/          # Block schemas
      section-blocks/  # Section block schemas (translations only)
      section-groups/  # Section group schemas
      types/           # Schema TypeScript types (SchemaSection, etc.)
    assets/
      scripts/
        entrypoints/   # Vite entrypoints (index.ts + store-specific UI modules)
        ui/            # Store-specific UI modules
      styles/          # Store-specific CSS (imports shared base)
  theme/               # Compiled Shopify theme (DO NOT edit generated files)
    sections/          # Liquid sections (schema JSON injected by build)
    snippets/          # Liquid snippets
    templates/         # JSON templates
    config/            # settings_schema.json, settings_data.json
    assets/            # Built CSS/JS/fonts (Vite output)
    locales/           # Translation files (generated by build)
```

### Shared Code

```
shared/
  scripts/
    entrypoints/base.ts   # Base bootstrapper (shared UI modules)
    utils/                 # Shared utilities (debounce, focus-trap, media-query, etc.)
  styles/                  # Base Tailwind CSS, shared variables
```

Changes to `shared/` affect ALL stores. Use commit scope `chore(shared):`.

### Build System

```
build/
  core/
    orchestrator.ts        # Build phase orchestrator
    schema/                # TS → JSON/Liquid schema pipeline
  scripts/                 # Dev/build CLI scripts
  plugins/                 # Custom Vite plugins
```

### Environment

The active store is controlled by `CURRENT_STORE` env var (default: `moominarabia`). Development commands:

```bash
npm run dev              # Interactive store selection
npm run dev:moominarabia # Direct store dev
npm run build:prepare -- --store moominarabia  # Build specific store
```

## Liquid Development

### Prefer `{% liquid %}` tag

Use the multi-line `{% liquid %}` tag for logic-heavy blocks. This is the project standard:

```liquid
{% liquid
  assign product_title = product.title | escape
  assign price = product.price | money
  assign is_available = product.available

  if is_available
    echo '<span class="text-green-700">Available</span>'
  else
    echo '<span class="text-red-700">Sold Out</span>'
  endif
%}
```

### `render` over `include`

Always use `render` for snippets. It creates an isolated scope, preventing variable leakage:

```liquid
{% comment %} Pass all needed data explicitly {% endcomment %}
{% render 'product-card', product: product, show_vendor: true, image_ratio: 'square' %}

{% comment %} NEVER rely on global scope {% endcomment %}
{% comment %} BAD: {% render 'product-card' %} {% endcomment %}
```

### Assign once, use multiple times

```liquid
{% liquid
  assign image_url = product.featured_image | image_url: width: 800
  assign image_alt = product.featured_image.alt | escape
%}

<img src="{{ image_url }}" alt="{{ image_alt }}" loading="lazy" width="800" height="800">
```

### Limit and paginate loops

```liquid
{% comment %} Always limit collection loops {% endcomment %}
{% for product in collection.products limit: 12 %}
  {% render 'product-card', product: product %}
{% endfor %}

{% comment %} Paginate large collections {% endcomment %}
{% paginate collection.products by 24 %}
  {% for product in collection.products %}
    {% render 'product-card', product: product %}
  {% endfor %}
  {% render 'pagination', paginate: paginate %}
{% endpaginate %}
```

For more patterns, see [references/liquid-patterns.md](references/liquid-patterns.md).

## TypeScript Schema System

Schemas are authored in TypeScript and compiled to JSON by the build system. The build injects the JSON into Liquid files between `{% schema %}` and `{% endschema %}` tags.

### Section Schema Pattern

Sections export a default object typed as `SchemaSection`:

```typescript
import type { SchemaSection } from '@/schemas/types/schemaTypes';
import { HeaderSetting, PaddingTopSetting, PaddingBottomSetting, ThemeSetting } from '@/schemas/settings';
import { HeadingBlock, RichTextRowBlock, ButtonBlock } from '@/schemas/blocks';

const sectionName = 'Product Grid';

export default {
  name: sectionName,
  tag: 'section',
  enabled_on: {
    templates: ['collection'],
  },
  settings: [
    HeaderSetting({ content: 'Layout' }),
    PaddingTopSetting(),
    PaddingBottomSetting(),
    ThemeSetting(),
  ],
  blocks: [HeadingBlock(), ButtonBlock()],
  presets: [
    {
      name: sectionName,
      blocks: [{ type: 'heading' }],
    },
  ],
} as SchemaSection;
```

### Setting Factories

Reusable setting factories live in `src/schemas/settings/`:

```typescript
import type { TextSchemaType } from '@/schemas/types/schemaTypes';
import { snakifyString } from '@shared/scripts/utils/snakifyString';

export const TextSetting = ({
  id = 'text',
  defaultValue = '',
  label = 'Text',
  placeholder = '',
  info = '',
  visibleIf = '',
} = {}): TextSchemaType => ({
  type: 'text',
  id: snakifyString(id),
  default: defaultValue,
  label,
  defaultLabel: 'Text',
  ...(placeholder && { placeholder }),
  ...(info && { info }),
  ...(visibleIf && { visible_if: visibleIf }),
});
```

### Config Schemas

Theme settings use named exports following the `{PascalCaseName}Config` convention:

```typescript
import { HeaderSetting, SelectSetting } from '@/schemas/settings';

const configName = 'Cart';

export const CartConfig = () => ({
  name: configName,
  settings: [
    HeaderSetting({ content: 'Cart recommendations' }),
    SelectSetting({
      id: 'cart_recommendations_intent',
      defaultValue: 'related',
      options: [
        { label: 'Related', value: 'related' },
        { label: 'Complementary', value: 'complementary' },
      ],
    }),
  ],
});
```

### Build Phases

The orchestrator (`build/core/orchestrator.ts`) runs these phases:

1. **BARREL** -- Generate index files for schema imports
2. **JSON** -- Process JSON schema files (parallel with SCHEMA)
3. **SCHEMA** -- Compile TS schemas to JSON, inject into `.liquid` files
4. **LOCALE** -- Merge locale/translation files

Run with: `npm run build:prepare -- --store {store}`

For the full schema type system and all setting types, see [references/schema-authoring.md](references/schema-authoring.md).

## Asset Pipeline

### Vite Entrypoints

Each store has a main entrypoint at `src/assets/scripts/entrypoints/index.ts`:

```typescript
import { initializeBase } from '@shared/scripts/entrypoints/base';
import { MyModule } from './ui/my-module';
import '@/assets/styles/main.css';

const storeModules = {
  'my-module': MyModule,
};

const bootstrapModules = (container?: Document | HTMLElement) => {
  initializeBase(storeModules, container);
};

bootstrapModules();

window.addEventListener('DOM:updated', (event) => {
  if (!event.detail.container) return;
  bootstrapModules(event.detail.container);
});
```

The `DOM:updated` event handles re-initialization after AJAX section rendering.

### CSS Pipeline

```css
/* Store CSS imports shared base then adds overrides */
@import '@shared/styles/base.css';
@import './variables/colors.css';
```

Tailwind v4 is integrated via `@tailwindcss/vite` -- no config file needed. Design tokens use `@theme` in CSS.

### Build Output

Vite outputs to `stores/{store}/theme/assets/` with naming:
- JS: `{name}.min.js`
- CSS: `{name}.min.css`
- Fonts: flat in `assets/` for Shopify CDN compatibility

### Path Aliases

| Alias | Resolves to |
|-------|------------|
| `@` | `stores/{store}/src` |
| `@/assets` | `stores/{store}/src/assets` |
| `@/schemas` | `stores/{store}/src/schemas` |
| `@shared/*` | `shared/*` |
| `@build/*` | `build/*` |

## Shopify APIs for Themes

### Cart API (AJAX)

```typescript
// Add to cart
const response = await fetch('/cart/add.js', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ id: variantId, quantity: 1 }),
});

// Update cart
await fetch('/cart/update.js', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ updates: { [variantId]: newQuantity } }),
});

// Get cart
const cart = await fetch('/cart.js').then(r => r.json());
```

### Section Rendering API

Dynamically re-render sections without full page reload:

```typescript
const response = await fetch(`${window.location.pathname}?sections=${sectionId}`);
const data = await response.json();
const html = data[sectionId];

document.getElementById(sectionId).innerHTML = html;
window.dispatchEvent(new CustomEvent('DOM:updated', {
  detail: { container: document.getElementById(sectionId) },
}));
```

### Predictive Search API

```typescript
const response = await fetch(
  `/search/suggest.json?q=${encodeURIComponent(query)}&resources[type]=product,collection,page&resources[limit]=4`
);
const { resources } = await response.json();
```

For complete API patterns with error handling, see [references/storefront-api.md](references/storefront-api.md).

## Shopify Dev MCP Integration

This project has access to the Shopify Dev MCP server with these tools:

### Workflow

1. **Start**: Call `learn_shopify_api` with `api: "liquid"` to get a `conversationId`
2. **Search**: Use `search_docs_chunks` with the `conversationId` to find relevant docs
3. **Read**: Use `fetch_full_docs` to retrieve complete documentation pages
4. **Validate**: Use `validate_theme` after editing Liquid files to catch errors

### When to Use Each Tool

| Tool | Use Case |
|------|----------|
| `learn_shopify_api` | First call in any Shopify conversation; also call again when switching API context (e.g., from `liquid` to `admin`) |
| `search_docs_chunks` | Find documentation for a specific Liquid tag, filter, object, or API |
| `fetch_full_docs` | Read a complete documentation page after finding it via search |
| `validate_theme` | Validate Liquid files for syntax errors and hallucinated content after edits |
| `validate_component_codeblocks` | Validate Polaris component usage |
| `introspect_graphql_schema` | Explore Admin/Storefront GraphQL schemas |

### Available API Contexts

For `learn_shopify_api`, use `api: "liquid"` for theme work. Other contexts:
- `admin` / `admin-execution` -- Admin GraphQL API
- `storefront-graphql` -- Storefront GraphQL API
- `custom-data` -- Metafields and Metaobjects
- `functions` -- Shopify Functions

## i18n and Multi-Market

### Locale File Structure

```
stores/{store}/theme/locales/
  en.default.json            # DO NOT EDIT -- generated by build
  en.default.schema.json     # Schema translations -- safe to edit
  da.json                    # Language translations
```

**CRITICAL**: Never write to regular `.json` locale files (`en.default.json`). The build system generates these from schema translations. Only edit `*.schema.json` files for schema label translations.

### Translation Keys in Schemas

The build system automatically converts human-readable labels to translation keys:

```
"label": "Products per row"  →  "label": "t:sections.product-grid.settings.products_per_row.label"
```

### Shopify Markets

When Markets is configured, Shopify handles:
- Automatic hreflang tag generation
- URL structure (subfolders like `/en-us/`, `/da-dk/`)
- Currency and language switching

In Liquid, use:
- `{{ request.locale.iso_code }}` for current locale
- `{{ request.locale.root_url }}` for locale-aware URL prefix
- `{{ localization.available_languages }}` for language switcher

Run these before submitting a pull request:

```bash
npm run format          # Prettier formatting
```

## DO / DON'T Quick Reference

### DO

- Use `{% liquid %}` for multi-line logic blocks
- Use `render` for all snippet includes (isolated scope)
- Assign expensive operations once, reuse the variable
- Limit loops with `limit:` or `paginate`
- Use Shopify CDN image filters (`image_url`, `image_tag`)
- Use `loading="lazy"` for below-fold images
- Provide descriptive `alt` text on all images
- Use `data-*` attributes for JavaScript hooks (not inline handlers)
- Write all scripts in TypeScript with modules
- Use Tailwind CSS classes over custom CSS
- Run `theme:check` before every PR
- Use the Section Rendering API for dynamic content updates
- Dispatch `DOM:updated` after AJAX section rendering

### DON'T

- Don't edit generated files in `theme/assets/`, `theme/config/settings_schema.json`, or `theme/locales/en.default.json`
- Don't use `include` (use `render` instead)
- Don't use inline `onclick` handlers (use `data-*` attributes)
- Don't use `window.*` globals (use modules)
- Don't write custom CSS when Tailwind utilities exist
- Don't hardcode strings (use translation keys)
- Don't use unlimited loops on collections
- Don't skip `loading="lazy"` on below-fold images
- Don't edit `*.schema.ts` files without running `build:prepare` to regenerate
